# Platform host boundary (Prompt 0)

The portable preparation API is in `src/Port.Prepare`. `PreparationEngine.ValidateXap` accepts only the exact phone package in `config/supported-versions.json` and creates no output. `GamePreparationPipeline.Prepare` validates first, then takes an explicit new workspace and tool/dependency paths through `GamePreparationTools`. It extracts the phone package, produces the pinned ABI report, performs the guarded rewrite and hook pass, converts content, and returns the three output locations. The caller owns workspace cleanup and transactional install/activation. `PreparedGameVerifier.Verify(dllPath, contentRoot)` checks patch and content manifests against the embedded supported XAP/DLL pair and hashes every listed content output; it does not require the source XAP after installation.

The inspection and ABI tools accept `--versions <supported-versions.json>` so a host can invoke them from any working directory. The rewrite and hook APIs accept an explicit private preparation root. The pipeline supplies both; it does not call `Directory.SetCurrentDirectory`. `Port.Content.IContentAudioConverter` lets a host provide its own WMA-to-Ogg implementation. The Windows adapter still uses the pinned FFmpeg executable and hashes it before content output is created. A new platform must pin and verify its own converter, FNA/native libraries, and runtime pack before distribution; the current pins in `config/dependencies.json` and `config/content-tools.json` cover Windows only.

`src/Port.Host` contains the `HostPaths`, `IGameHostAdapter`, `IGameFilePicker`, and `IGamePhotoPicker` contracts. The Windows launcher implements the game adapter in `WindowsGameHostAdapter`: FNA window/display and desktop input hooks, save and picture paths, and packaged native DLLs. `RunSession` passes an explicit content root and save paths, and loads the verified game DLL from its supplied path. Four guarded phone `TitleContainer.OpenStream` calls now use `Port.Hooks.GameContent`, whose root is configured by the host. This allows program files, prepared content, and saves to occupy different directories. The original content and save formats are unchanged.

Windows-specific work remains in the Inno wizard (its XAP/art pickers and install transaction), Windows native packaging, and the Windows FFmpeg build. The Linux host now supplies app-data storage, native file/photo pickers, Linux libraries, and a Linux converter while reusing the desktop FNA display/input hooks. The [persistent import contract](platform-import.md) describes the shared first-launch transaction and Reimport lifecycle. The Windows creator still uses its folder picker. The FNA host and `Assembly.LoadFrom` have a Linux headless load/import check, with graphical gameplay still untested; macOS and mobile remain untested.

For local Windows development, `. .\dev.ps1; build-game` remains the required full check. `installer/build.ps1` builds the offline setup. The supported XAP fingerprint is `6b88c7fbd95444d2560b4b11e6f35d40a6c0f7abc30706155dcbccd18bc333fe`; its original DLL fingerprint is `7b819cb562826ae4d2592ff741877e76da0e57bfbe48192aabb79319fdb36823`. The Windows FNA source is 26.11, .NET SDK is 10.0.302, Mono.Cecil is 0.11.6, and the Windows converter is the pinned FFmpeg 8.1.1 build. Exact archive, binary, and native bundle hashes are in `config/`.

## Linux x64 host (Prompt 2 implementation)

`Z0MB1ES --linux` uses XDG data/state directories, Zenity GTK file dialogs and progress, the shared `PersistentAssetStore`, and a child `--run-managed` process for clean assembly reload after Settings Reimport. `LinuxGameHostAdapter` supplies the same FNA desktop display/input hooks with Linux native libraries and explicit save/picture roots. Creator photos use Zenity multi-file selection through the `P` shortcut in the picture mapper; selected PNG/JPEG files are copied into app data before the game loads them. The package includes unversioned library aliases because .NET P/Invoke probes `libSDL3.so`, `libFNA3D.so`, and `libFAudio.so` on Linux. The native bundle's versioned `.so.0` names remain available for their own dynamic dependencies.

The Linux ABI checker is published as a directory so its runtime assembly catalog remains visible; a single-file publish produced false unresolved references. The Linux report has the same semantic findings as Windows but LF line endings, and the rewriter pins its exact SHA-256 separately. The Linux FFmpeg executable is built from the corresponding source bundle and checked against `config/linux-converter.sha256` before import. Exact package inputs are in `config/linux-packaging.json`; package commands and remaining graphical acceptance are in the [Linux package guide](../../installer/linux/README.md).

## macOS host (Prompt 4 implementation in progress)

`Z0MB1ES --macos` uses `~/Library/Application Support/z0mb1es-rec0mp1led` for assets, saves, and copied creator photos, and `~/Library/Logs/z0mb1es-rec0mp1led` for logs. AppleScript system dialogs select the XAP, optional art, and PNG/JPEG creator photos. The shared import transaction and child `--run-managed` process provide first launch, repair, and clean session replacement after Reimport. The macOS adapter checks bundled SDL3, FNA3D, FAudio, and Theorafile dylibs and reuses desktop FNA display/input hooks. The package recipe places the self-contained launcher and tools in `Contents/MacOS`, and the icon/notices in `Contents/Resources`. The converter hash is checked before importing content. The [macOS package guide](../../installer/macos/README.md) records required build inputs and open acceptance; there is no Mac-built artifact yet.
