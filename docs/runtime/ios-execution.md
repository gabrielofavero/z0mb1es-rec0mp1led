# iOS execution decision and fallback design

Prompt 6 is **in progress; the initial Plan 1 feasibility probe passed on a device** on 2026-11-10. Build 2's user-supplied trace on iPhone 16 Pro / iOS 26.7.1 demonstrates UI startup, two newly generated IL payloads executing through reflection/delegates, exact XAP extraction and metadata roundtrip, picker cancellation and all three in-process song conversions. In response to the force-quit/reboot/Home Screen procedure, the user confirmed no JIT and both `persistent-il=passed` and `persistent-import=passed`. Those follow-up confirmations are manual evidence; a second raw startup trace was not supplied. The [probe guide](../../installer/ios/README.md) and [implementation log](../records/implementation-log.md) record the artifact identity and evidence. The initial black-screen packaging defect is resolved by build 2's `MtouchLink=None`, explicit scene configuration and packaged-code check. The player-facing FNA host now builds locally as `Port.IosGame`, with on-device preparation and optional artwork/photo import. Build 4 reached its first Metal frame but displayed no importer. Build 5 changes that startup presentation path; device confirmation remains pending. Original-game device execution remains unobserved; the prerequisite result does not establish Prompt 6's all-mode acceptance. The user declined further diagnostic installations and requested the real player build.

## Decision criteria

Keep original phone gameplay as the preferred path if ordinary Home Screen launches after signing/installing with a compatible sideloading tool can interpret the locally rewritten game reliably, including fresh launch after reboot, all modes, media time, saves, and acceptable performance. This is **Plan 1**: publish one content-free IPA and import the player's XAP on the device. Avoid NativeAOT for dynamic assembly import. Plan 1 requires neither per-launch JIT nor a player-managed compiler/toolchain. Original game code stays out of public downloads; Plan 2 below separately investigates guided player-built IPAs.

The generated-IL probe isolates one prerequisite. It cannot prove original-game ABI compatibility, interpreter handling of every generic/reflection path, native callbacks, graphics, audio, or performance. The implementation now links FNA 26.11 and five pinned device static libraries, supplies an in-process preparation/ABI runner with the exact reviewed Mono runtime catalog, and loads the verified original game. Build 4 presents normal import/play controls rather than the superseded build-3 mode-check UI. Actual play of every mode remains the next source of device evidence. Record native exceptions/crash reports, memory peaks, frame times and song clock drift. The desktop `RuntimeHelpers.PrepareMethod` sweep is not an iOS acceptance test.

If generated IL fails, preserve the Release build properties, full exception/native crash, payload hash, and a second run without a debugger/JIT service before concluding the configuration is unusable. If synthetic IL passes but the game fails, isolate the first actual ABI/runtime/interop problem before choosing a replacement. Toolchain absence does not invalidate the interpreter design.

## Plan 2 — Guided local player build on Mac only (contingent, not implemented)

If Plan 1 cannot execute the imported game reliably or with acceptable performance, investigate compiling the player's prepared game assembly into a personal IPA. This preserves original gameplay as the goal before considering an authored replacement. AOT compilation is a candidate, not a demonstrated solution: the original assembly, hooks, generics/reflection, native callbacks and FNA must all work with the selected iOS compilation configuration. Simply adding a DLL or assets to an existing IPA does not resolve an execution failure.

Supply one guided command-line entry point for a compatible Mac. It should ask for the supported XAP and independent optional art sources, validate them with the shared guards and detect local build prerequisites. A graphical installer/wizard may wrap the same preparation/build operations; keep the command-line route fully documented and usable on its own. These are planned interfaces, not existing commands. The local build produces a personal unsigned IPA and checksum, then explains signing/install with a compatible tool.

### Guided local build

1. Provide a short start-to-finish Mac guide: get the selected source release and helper, launch one command, then follow its prompts. Check supported macOS, full Xcode (not only Command Line Tools), selected developer directory, pinned .NET SDK/iOS workload and native build prerequisites. Explain missing tools and required Xcode first-launch/license steps, then allow retry after setup. Do not promise automatic installation of every prerequisite.
2. Ask for the player's XAP and optional sources using quoted paths or a file picker. Validate before mutation, prepare/patch the game assembly, convert assets and compile the assembly together with the host using the selected iOS AOT configuration. Keep source packages intact, all proprietary output in ignored local storage, and retain the last successful IPA if a later build fails.
3. Show build stages, actionable errors, the output IPA path and checksum. Package the selected prepared assets in the personal IPA and initialize app-private persistent content from them on first launch, preserving the phone XAP as the complete original-art fallback. Keep saves separate from replaceable content and preserve asset-only Reimport.

Plan 2 requires access to a Mac that supports the pinned toolchain. It needs no GitHub account and keeps the game code/assets and personal IPA on that Mac. Non-Mac builds, remote Mac services, GitHub fork builds, online asset transfer and shared backends are outside the current Plan 2 scope. Revisit alternatives only if Plan 1 fails and there is evidence that local AOT compilation works.

### Signing, updates and acceptance

Signing/install tools can include [AltStore Classic/AltServer](https://faq.altstore.io/altstore-classic/altserver), [Sideloadly](https://sideloadly.io/) or another validated route; AltStore is an example, not a dependency. Keep Apple credentials in the selected signing tool. Document and validate the selected tool’s Mac signing/install/renewal steps for this local build.

Reuse a completed personal IPA for signing renewal; renewal alone must not require recompilation. Rebuild when compiled game/host changes require it, preserve bundle identity and app-private saves, and distinguish asset-only reimport from code changes that require a new IPA. Validate each advertised signing tool with the actual IPA and record its version/options; a successful test with one tool does not establish support for another.

Before selecting Plan 2, demonstrate a personal AOT build on a real iPhone through a normal launch after reboot, all three modes, graphics/audio, acceptable performance and save-preserving updates. Before documenting the player workflow as supported, verify the guided local build on a compatible Mac, prerequisite failures, cancellation/retry, preservation of source files and the last successful IPA, cleanup and the documented signing handoff. A graphical wrapper must call the same verified operations. Plan 2 is unimplemented and does not close Prompt 6. Review personal packaging and third-party dependencies before offering the build tooling; this design does not establish distribution rights.

**Preference if both pass:** Choose Plan 1 when it meets gameplay and performance acceptance: one public IPA, local-only import and simpler updates without a player build. Plan 2 is the fallback for a measured execution/performance problem that justifies local toolchain setup on a compatible Mac. Both require device signing and renewal.

## Authored-gameplay alternative (after Plans 1 and 2, contingent, not implemented)

If neither on-device interpretation nor personal compilation provides a viable original-game execution path, assess shipping authored gameplay compiled into the IPA and importing **data only**. The same gameplay assembly can later target an Android-supported renderer. Its proposed boundaries are:

| Component | Responsibility and preservation requirement |
| --- | --- |
| `Mobile.Gameplay.Core` | Framework-independent fixed-step simulation, mode state machines, collision, spawning, scoring and achievements. Inputs are authored action records and a song-clock snapshot; outputs are draw/audio events and state snapshots. No runtime reflection into phone types. |
| `Mobile.Gameplay.Normal` | Recreate original `ZombieGame.Init(false)` / `Play(false)` behavior: movement/aim, enemies and projectiles, song-phase director, deaths, win/end state, score thresholds. Menu/play states correspond to original 2/3. |
| `Mobile.Gameplay.Endless` | Recreate `ZombieGame.Init(true)` / `Play(true)`, room scrolling, rounds, enemy progression and powerups with its independent music clock. Preserve round-completion achievements and normal/Endless distinctions. Original states are 6/7. |
| `Mobile.Gameplay.Viking` | Recreate `VikingGame.Init` / `Play`, character movement/attack, tower cells and scrolling, moon interactions, song phases, height/score and ending conditions. Original states are 4/5. |
| `Mobile.Gameplay.Presentation` | Scene/menu state, animation, particles, sprites and audio events driven by simulation state; renderer consumes imported phone textures/fonts/scenes and optional mapped art. Reproduce the original 600×360 behavior before adapting mobile aspect/safe areas in Prompt 7. |
| `Mobile.DataImport` | Exact XAP guard; XNB/scene/map decoding and the in-process song converter; explicit schemas for imported asset references and declarative tables. It must never load the game assembly as executable code. Optional-art inputs remain optional and independent. |
| `Mobile.SaveCodec` | Implement the original version-101 stream format independently from its observed schema, with golden local fixtures for profile, player and customizer data. Preserve original backups until a new format/roundtrip is verified; do not overwrite a desktop save merely because fields appear similar. |
| `Mobile.Host` | Statically compiled iOS game entry point, system pickers, persistent transaction, graphics/audio, input, suspend/resume and photo import. Android later implements the same services using its selected runtime. |

The state numbers and entry points above are established by the current [mode evidence](../records/feature-matrix.md) and authored desktop `ModeProbe`; they are not a complete gameplay specification. No claim of exact parity follows from them. Multiplayer/player-count behavior, random sequence, scene choreography, enemy rules, score formulas and endings require explicit evidence before implementation.

Build an evidence ledger per system from controlled runs of the user-owned XAP. Record action sequences, fixed elapsed times, song positions, state transitions, entity snapshots, collision outcomes, score/achievement changes and save bytes. Label anything inferred from original IL. Extracted numerical tables, choreography and metadata remain local; distribute only authored extraction recipes and schema/hash guards. Do not smuggle a bytecode interpreter or a translated method instruction stream into a supposedly data-only import. Behavior embedded in code must be reimplemented as authored code from an independently reviewed specification.

Implement the common world/action/save contracts first, then one complete original-art Normal cycle, Endless rooms/rounds, and Viking tower/ending. For each system, replay the same controlled input sequence through the original desktop runtime and authored engine, normalize observation fields, and compare timing/state/events. Use original phone hardware observations when available; desktop hooks are not a golden oracle. Complete long-form play and audiovisual comparisons after the short mode cycles. Retain separate legacy and authored save fixtures until every serializer field and achievement trigger has a documented mapping.

## Preservation and licensing limits

This alternative changes the gameplay implementation and introduces a substantial parity risk. The existing project intentionally executes original phone logic; the old decompiled project cannot become the source for a bundled replacement. Keep specs, observations and independently written implementation provenance distinct. No decompiled methods, original strings/tables, choreography or media may be checked in or bundled merely because they are easy to recover. Player ownership and local import do not by themselves settle distribution rights. The existing release rights review must cover the authored implementation, extraction recipes and dependency licenses before publication.

This document records two original-game execution candidates and an authored-gameplay alternative with the evidence work needed. It does not select a fallback or close the plan's acceptance gate: imported IL has not failed on a device, personal AOT compilation has not been tested, and the replacement's complete behavior specification and preservation review do not yet exist. Continue Prompt 6 until one route has sufficient evidence; leave Prompts 7–9 open.
