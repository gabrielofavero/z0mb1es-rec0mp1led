# Platform expansion plan

**Status:** Windows implementation and Prompt 0 complete. Prompt 1 shared import transaction is implemented. Prompt 2 has a Linux x64 host and local `.deb`/`.rpm` artifacts, but its graphical install, visible first-launch UI, and playable desktop acceptance remain open because the available WSL environment has no graphical session. Linux is not a published release. Prompt 4 now has macOS host and packaging source, but no Mac-built `.app` or `.pkg`; exact native hashes and macOS acceptance are open. iOS and Android remain planned. macOS, iOS, and Android are homebrew releases: no app store, paid developer program, publisher certificate, or player-side build. Players receive prebuilt downloads, then provide their own supported game package and any optional art sources. For iOS, **AltStore Classic** handles the per-device signing of a prebuilt IPA using the player's regular Apple ID; for Android, the release build applies the APK signature the OS requires using a local key. Neither calls for a paid developer account or a player-compiled build.

## Current baseline and major constraints

- Windows is the completed implementation baseline. Its Inno Setup executable verifies a user-supplied XAP, rewrites its game DLL, converts content, and installs a self-contained FNA/.NET launcher. See the [installer contract](../../../installer/README.md) when adapting shared code for other platforms.
- `Port.Launcher` loads the prepared `ZombiesWP7.dll` with `Assembly.LoadFrom`, and `PreparedGameVerifier` now checks the DLL and content at explicit locations; guarded custom-file calls use the supplied content root. `Port.Launcher.csproj` packages Windows x64 native libraries. `DesktopDisplay`, `DesktopInput`, `DesktopPictures`, `DesktopStorage`, and phone service fallbacks contain Windows or desktop assumptions. These are specific refactoring targets, not portable as-is.
- `Port.Content` currently starts a pinned `ffmpeg.exe` process to convert three WMA songs to Ogg. Linux/macOS need tested native converter builds; mobile needs an in-process, platform-supported conversion or decoding path. A mobile app cannot be treated as a repackaging of this Windows helper.
- The [optional asset swap plan](../done/2026-11-07-asset-swap.md) is complete. Its supported Steam/360 art imports must remain optional, with the phone XAP as the complete original fallback.
- [FNA supports macOS and iOS](https://fna-xna.github.io/docs/appendix/Appendix-C%3A-FNA-on-Apple-Platforms/), but [FNA explicitly does not support Android](https://fna-xna.github.io/docs/0%3A-FAQ/). Android needs a different supported renderer/runtime, likely a MonoGame mobile host, with ABI/content and gameplay validation rather than an assumed drop-in swap. [MonoGame lists both mobile targets](https://docs.monogame.net/articles/getting_started/platforms.html).
- iOS installation is via [AltStore Classic and AltServer](https://faq.altstore.io/altstore-classic/altserver), using a regular Apple ID rather than publisher signing or App Store review. [AltStore says free-account apps expire after seven days and must refresh](https://faq.altstore.io/altstore-classic/your-altstore); AltServer normally runs on a Windows or Mac computer on the same network for refresh. This is a real user setup cost to document, not a reason to drop the IPA path. AltStore PAL is a different, notarized distribution route and is outside this plan.
- The remaining iOS gate is technical: device builds use ahead-of-time compilation or an interpreter, and the current on-device import/IL rewrite/`Assembly.LoadFrom` flow must be proven on a real iPhone. AltStore installation alone does not establish that the imported game DLL can execute. A design that requires users to manually enable JIT each launch would conflict with the simple-install goal.
- [Android requires every APK to be signed before installation](https://developer.android.com/studio/publish/app-signing). Apply that signature automatically in release packaging with a retained local key; players only allow installation from the browser/file manager and install the APK. There is no developer account or store involved.

## Shared import and runtime contract

1. Split the current desktop host into platform-neutral preparation, content, manifest, save, and game-facing services plus platform-specific window/input/display, file picker, photo picker, storage, and native library adapters. Keep the original phone DLL and proprietary files out of release artifacts. Version-pin all supported input fingerprints and tool/native dependencies for each platform.
2. On first launch with no valid base install, show an import screen. Require the supported phone XAP; offer optional supported I MAED and Time Viking art packages/directories. Validate before mutation, show source/version and needed storage, prepare into a staging area, verify hashes, and atomically activate it. Mark onboarding complete only after a successful base import. Cancel or failure keeps the importer available next launch.
3. Store prepared assets and manifests in app-controlled **persistent data**, separate from saves and the read-only program package. The game must load from this location, including after restart/update. After successful import, original XAP/Steam/360 packages can be deleted without breaking play. The app must not depend on remembered source paths. Retain the previous working asset set until replacement commits; never erase saves during reimport. Explain that uninstalling the app can remove its private imported data and saves, so backup/export may be a later feature.
4. In **Settings → Assets → Reimport**, reopen the same picker. Allow replacement of the base XAP and each existing optional source, and addition of missing optional sources. A canceled or failed import leaves the current game intact. On successful commit, save preferences, dispose the running game, and start a fresh game session so all content is reloaded. Do not ask for packages on ordinary boots once a valid install exists. The existing optional-art selection settings remain independent of the reimport action.
5. Put save paths, generated assets, logs, and manifests under each platform's app data conventions. Continue using explicit storage paths without `Directory.SetCurrentDirectory` or a same-directory constraint. Verify generated files against the manifest at launch, offer repair through Reimport if corrupt, and preserve saves across updates and repair. Avoid broad filesystem/photo permissions when system pickers suffice.

## Display, input, and creator behavior

- Mobile has no resolution or fullscreen settings. Render landscape content to the current **usable window** with a uniform scale, fill the available width, and adjust the logical scene's width or height to the actual aspect ratio without stretching sprites. Keep a minimum scene area so original menus and gameplay fit. Place touch controls inside safe areas around cutouts, rounded corners, and system bars; test narrow, wide, tablet, and split-screen windows.
- Recompute scene size, render targets, menu positions, and the touch/mouse coordinate transform when the usable window changes. Preserve game state on rotation, Android fold/unfold or multi-window resize, and iPad window changes. If a fold hinge divides the window, keep primary UI and touch controls in safe regions. This is a required continuity test, not only an optional resolution tweak. [Android documents fold/window changes](https://developer.android.com/guide/topics/large-screens/configuration-and-continuity).
- Keep touch as the default mobile input. Support connected controller plus mouse/keyboard where the OS and device expose them; map all through the same game actions, handle hot plug/disconnect, focus, back/cancel, and pointer scaling. Hide touch overlays only when the player chooses or when a verified input mode makes that useful.
- Replace the Windows-only creator folder picker with native multi-photo selection: [iOS Photos picker](https://developer.apple.com/documentation/PhotoKit/delivering-an-enhanced-privacy-experience-in-your-photos-app) and [Android Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker). Decode JPEG, PNG, and HEIC/HEIF where the platform supplies them; apply EXIF orientation and color conversion; bound image count, size, and memory; create thumbnails and game textures on the correct graphics thread. Copy selected images or normalized thumbnails into app data so creations still work if the original photo changes or picker access expires. Preserve the current custom sprite save format or migrate it explicitly. System pickers avoid broad library permission for this workflow.

## Implementation prompts

Windows is complete for this plan. Run the prompts below **in order**, one at a time, starting with the shared work needed for Linux. Each prompt is intended to be pasted into a coding-agent session. Before starting, read the platform constraints and player contract above, the [completed Windows prompts](../done/2026-11-06-initial-implementation/implementation-prompts.md), the [optional art contract](../done/2026-11-07-asset-swap.md), and the repository instructions. Record commands, supported input fingerprints, device observations, and remaining gaps in `docs/records/implementation-log.md`; update the feature matrix and relevant player documentation. Keep the original phone DLL, XAP, optional source files, and generated proprietary assets out of tracked files and release packages. For each code change, pass the repository's required `build-game` check as well as the platform-specific checks. Complete a prompt's acceptance gate before moving to the next; if evidence invalidates the design, revise the affected prompt and record why.

### Prompt 0 — Extract portable host and preparation boundaries (complete)

Refactor the completed Windows implementation into platform-neutral XAP validation, guarded DLL preparation, content manifest, game-facing services, and save contracts, with adapters for window/display/input, storage, native libraries, and file/photo pickers. Remove same-directory and `Directory.SetCurrentDirectory` assumptions from the portable path. Pin accepted XAP fingerprints and tool/native dependency versions. Keep the Windows installer and player behavior working while making the portable pieces callable from a new host. Document which Windows-specific hooks remain and how another host supplies them.

**Acceptance:** The shared APIs can validate and prepare a supported XAP without a Windows UI or hard-coded executable directory. Existing Windows setup, optional-art selection, launch, and saves still work; unsupported inputs fail before changing an install.

### Prompt 1 — Build persistent first-launch import and Reimport (shared layer implemented)

Implement the common import transaction for new hosts: an app-owned persistent asset location separate from the read-only package and saves; native file selection; source/version and space preview; staging, hash verification, and atomic activation. Require the phone XAP and offer the supported I MAED and Time Viking sources independently. Importing only the XAP must yield a complete original-art install. Keep the previous asset set until replacement succeeds, never erase saves, and never require original package paths after commit. On ordinary starts, verify the prepared manifest and launch directly when valid. Add **Settings → Assets → Reimport** to replace the base or optional sources and add missing ones; cancellation/failure keeps the current game usable. After a successful commit, persist preferences, dispose the old game session, and start a fresh one. Offer repair through the same UI when verification fails.

**Acceptance:** First import, restart, update, replacement, addition, cancel, corrupt input, and failed staging behave transactionally. Players can delete their original packages after import and still play; saves and optional-art preferences survive reimport. The importer returns after an incomplete onboarding attempt.

**Acceptance boundary discovered during implementation:** No new-platform executable or package exists before Prompt 2, so native file dialogs, visible progress, game-process restart, and player first-launch behavior cannot be run as end-to-end acceptance here. Prompt 1 must prove the shared transaction and picker/view/session contracts with real prepared manifests and failure injection. Prompt 2 must implement the Linux host adapters and close the remaining Prompt 1 player-flow acceptance before packaging is considered complete. The Windows Setup path remains the existing Windows importer.

### Prompt 2 — Make Linux x64 playable and package it

Port launcher, hooks, bridge, input/display, storage, native library loading, and font/audio/video behavior to Linux. Package supported Linux builds of SDL3, FNA3D, FAudio, and the pinned WMA-to-Ogg converter instead of invoking `ffmpeg.exe`. Use the Prompt 1 first-launch importer and native file/photo selection. Produce a self-contained `.deb` with desktop entry and icon, then an `.rpm`; package scripts should install the authored application without prompting for a XAP. Keep generated content in app data. Document reproducible build commands and native dependency versions.

**Acceptance:** Both packages install through a graphical package manager and open the importer on first launch without an SDK, terminal, or extra downloads. The installed app launches from its desktop entry with no reliance on the build tree or source packages.

### Prompt 3 — Validate the Linux release path

On native Linux hardware, exercise clean install, update, removal, import and Reimport, bad/corrupt XAP handling, all three game modes, Settings, creator photos, keyboard/mouse, controller, audio, saves, and optional-art fallback. Use a VM for clean package checks only where graphics acceleration is sufficient. Audit `.deb` and `.rpm` payloads for proprietary material; document what removal does to app data and saves. Fix failures before recording final package checksums and player install instructions.

**Acceptance:** A player installs either package, imports their XAP once, plays every mode, and can repair or reimport without developer tools. Updates preserve prepared assets and saves; optional-art failure leaves original art usable.

### Prompt 4 — Build the macOS app and unsigned package

Port native libraries, file/photo pickers, input, app-bundle resources, storage, and WMA conversion to macOS. Build a self-contained `.app` and unsigned `.pkg` on macOS; keep generated content and saves outside the bundle. Pin the Xcode/.NET/native toolchain. Package Apple Silicon and Intel variants only when each has a tested build and matching native libraries. Use the common first-launch import and Reimport contract. Document the exact macOS **Open Anyway** procedure for the unsigned package ([Apple instructions](https://support.apple.com/en-us/102445)).

**Acceptance:** A fresh macOS install opens the importer after the documented security override; it needs no SDK, account, publisher certificate, or original packages in the app bundle. A package audit finds no proprietary files.

### Prompt 5 — Validate the macOS release path

On real Mac hardware for each promised architecture, test fresh install/update, Gatekeeper override, first import, Reimport and repair, all game modes, controller/mouse/keyboard, creator photos, audio, and save preservation. Check that launch works through Finder and that canceling or failing an import leaves the prior install intact. Publish checksum and concise homebrew download instructions after the package audit and rights review.

**Acceptance:** A Mac user can install the unsigned package, perform the one-time security override, import their XAP, play, and update without developer tools or an account.

### Prompt 6 — Prove the iOS execution path on a real device

Create the smallest content-free `ios-arm64` IPA that AltStore Classic can install with a regular Apple ID. On a real iPhone, prototype on-device XAP preparation, three-song conversion without a spawned desktop executable, persistent asset storage, and execution of the prepared game assembly under a supported iOS interpreter/AOT configuration. Test a normal AltStore launch without manually enabling JIT each time; a simulator is insufficient. Use [.NET iOS runtime guidance](https://learn.microsoft.com/en-us/dotnet/maui/deployment/runtimes-compilation?view=net-maui-10.0) and verify the actual host's [`EnableCodeSigning`/`BuildIpa` settings](https://github.com/dotnet/macios/blob/main/docs/building-apps/build-properties.md). If imported executable IL cannot run reliably, assess an authored, statically bundled gameplay implementation that imports data/assets only, including its preservation and licensing constraints. Record the chosen path and a device trace.

**Acceptance:** A real-device prototype demonstrates a viable content-free execution path for all three phone modes, or the plan records a concrete authored-gameplay design that can do so. Do not claim iOS playability from AltStore installation or simulator results alone.

### Prompt 7 — Implement shared mobile import, display, input, and photos

Adapt Prompt 1 for mobile system file pickers and app-private persistent storage, with no broad filesystem permission. Render landscape gameplay to the current usable window with uniform sprite scaling, width filling, an aspect-adjusted logical scene, minimum menu/gameplay area, and safe-area touch controls. Rebuild render targets, layout, and pointer transforms on rotation, iPad window resize, Android multi-window resize, and fold/unfold while preserving game state; keep primary controls clear of a fold hinge. Support touch by default and map controller, mouse, and keyboard to the same actions with hot plug, focus, and back/cancel handling. Replace the desktop creator folder picker with iOS Photos picker and Android Photo Picker adapters. Normalize JPEG/PNG and platform-supported HEIC/HEIF with EXIF orientation and color handling, bounded memory/count, graphics-thread texture creation, and copied app-data thumbnails so creations survive source changes. Preserve or explicitly migrate the custom sprite save format.

**Acceptance:** Mobile import and Reimport survive restart/update, bad input, and source deletion. On narrow, wide, tablet, and resizable windows, menus and play remain visible, touch targets remain safe, input aligns with drawing, state survives size changes, and creator images persist without broad photo-library access.

### Prompt 8 — Build and distribute the iOS IPA

Implement the Prompt 6 execution choice and Prompt 7 mobile services in an iPhone host. Pin compatible Xcode, .NET SDK, and iOS workload in a reproducible macOS workflow; build a prebuilt `ios-arm64` IPA with publisher code signing disabled, audit it for proprietary material, and publish the tested artifact with checksum. A GitHub-hosted macOS runner is acceptable for repeatable builds. Start with a direct IPA download; add an AltStore Classic source JSON only after direct install/update works. Keep AltStore PAL and paid developer-program signing out of this release path. Provide short setup instructions for AltServer on Windows/Mac, regular Apple ID, trust/Developer Mode, and seven-day refresh.

**Acceptance:** AltStore Classic installs the prebuilt IPA on a real iPhone without a player build or paid account. The app imports the XAP through a system picker, launches all three modes, and contains no bundled proprietary content.

### Prompt 9 — Validate iOS install, play, and refresh

With a regular Apple ID and real device, test initial AltStore install, import and Reimport, app update under the same AltStore identity, AltServer refresh at the seven-day boundary, and preservation of imported assets, preferences, creations, and saves. Exercise all three modes, graphics/audio, touch/controller input, photo selection, rotation/window changes where supported, failure recovery, and storage pressure. Document exact device/iOS versions and any remaining constraints.

**Acceptance:** A player installs the prebuilt IPA, imports their XAP once, plays and reimports, updates, and refreshes through AltStore Classic without building the app or joining the paid Developer Program.

### Prompt 10 — Prove an Android game host on a real device

Because FNA does not support Android, prototype a supported host such as MonoGame on a physical Android device. Measure XNA ABI/content compatibility, native graphics/audio/input behavior, and whether the prepared `ZombiesWP7.dll` can load and run after on-device import. Reuse the authored mobile gameplay path if executable code import is not robust. Record device/API/ABI coverage, the gaps found, and the smallest supported implementation path; do not treat a desktop FNA build as Android evidence.

**Acceptance:** The selected host demonstrates a viable path to all three modes with user-imported data on a real device, or identifies a concrete authored-gameplay port and its remaining work before APK packaging begins.

### Prompt 11 — Build the signed Android APK

Implement the Prompt 10 host using shared mobile import, display/input, photos, and save services. Produce a prebuilt APK with pinned SDK/JDK/.NET Android tooling. Create and retain a private release signing key outside tracked source, sign every release APK automatically, and preserve key continuity for updates ([Android signing requirements](https://developer.android.com/studio/publish/app-signing)). Audit the payload for proprietary files. Write player instructions for browser/file-manager installation, unknown-sources permission, first import, and any advanced sideload flow required on affected certified devices as [developer verification](https://developer.android.com/developer-verification/guides/faq) expands.

**Acceptance:** The signed APK installs and updates directly on a real device, opens the first-launch importer, and runs all three modes without a store, developer account, computer, or player-side build.

### Prompt 12 — Validate Android play, continuity, and repair

Test direct install/update, optional-source combinations, bad/corrupt import, Reimport and repair, all modes, creator photos, touch/controller/keyboard/mouse, background/resume, fold/unfold and multi-window resizing, storage pressure, and deletion of original source packages. Include at least one resizable or foldable environment and physical phones for graphics/audio/input. Confirm the signed update preserves assets, settings, creations, and saves. Check current sideload behavior on affected certified devices, record exact device/API results, and publish checksums and concise install instructions.

**Acceptance:** A user downloads the APK, grants the required device install permission, imports packages once, can delete those packages, and plays or reimports without a computer or developer account.

## Decisions to revisit at the mobile gate

- Whether the prepared phone DLL can execute on iOS under a normal AltStore launch, using a supported interpreter configuration without a manual JIT step. This is the main iOS feasibility gate after choosing AltStore for installation.
- Whether an optional AltStore Classic source improves updates enough to justify its maintenance; a direct IPA is the initial artifact.
- Whether a distributable authored mobile game implementation is possible within the project's preservation and licensing constraints. This decides the technical iOS path if distribution is later possible and whether Android can share one code path.
- Exact supported mobile OS versions, device GPU targets, and storage budget after real-device prototypes; do not pin them from desktop assumptions.
