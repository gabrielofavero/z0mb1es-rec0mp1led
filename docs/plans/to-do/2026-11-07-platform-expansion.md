# Platform expansion plan

**Status:** Planned. Priority order: Windows, Linux, macOS, iOS, Android. macOS, iOS, and Android are homebrew releases: no app store, paid developer program, publisher certificate, or player-side build. Players receive prebuilt downloads, then provide their own supported game package and any optional art sources. For iOS, **AltStore Classic** handles the per-device signing of a prebuilt IPA using the player's regular Apple ID; for Android, the release build applies the APK signature the OS requires using a local key. Neither calls for a paid developer account or a player-compiled build.

## Current baseline and major constraints

- Windows has an Inno Setup executable that verifies a user-supplied XAP, rewrites its game DLL, converts content, and installs a self-contained FNA/.NET launcher. Release acceptance is still open; see [installer status](../../../installer/README.md).
- `Port.Launcher` loads the prepared `ZombiesWP7.dll` with `Assembly.LoadFrom`, and `RunSession.VerifyInputs` requires that DLL and content beside the launcher. `Port.Launcher.csproj` packages Windows x64 native libraries. `DesktopDisplay`, `DesktopInput`, `DesktopPictures`, `DesktopStorage`, and phone service fallbacks contain Windows or desktop assumptions. These are specific refactoring targets, not portable as-is.
- `Port.Content` currently starts a pinned `ffmpeg.exe` process to convert three WMA songs to Ogg. Linux/macOS need tested native converter builds; mobile needs an in-process, platform-supported conversion or decoding path. A mobile app cannot be treated as a repackaging of this Windows helper.
- The [optional asset swap plan](../in-progress/2026-11-07-asset-swap.md) is planned, not implemented. Its supported Steam/360 art imports must remain optional, with the phone XAP as the complete original fallback.
- [FNA supports macOS and iOS](https://fna-xna.github.io/docs/appendix/Appendix-C%3A-FNA-on-Apple-Platforms/), but [FNA explicitly does not support Android](https://fna-xna.github.io/docs/0%3A-FAQ/). Android needs a different supported renderer/runtime, likely a MonoGame mobile host, with ABI/content and gameplay validation rather than an assumed drop-in swap. [MonoGame lists both mobile targets](https://docs.monogame.net/articles/getting_started/platforms.html).
- iOS installation is via [AltStore Classic and AltServer](https://faq.altstore.io/altstore-classic/altserver), using a regular Apple ID rather than publisher signing or App Store review. [AltStore says free-account apps expire after seven days and must refresh](https://faq.altstore.io/altstore-classic/your-altstore); AltServer normally runs on a Windows or Mac computer on the same network for refresh. This is a real user setup cost to document, not a reason to drop the IPA path. AltStore PAL is a different, notarized distribution route and is outside this plan.
- The remaining iOS gate is technical: device builds use ahead-of-time compilation or an interpreter, and the current on-device import/IL rewrite/`Assembly.LoadFrom` flow must be proven on a real iPhone. AltStore installation alone does not establish that the imported game DLL can execute. A design that requires users to manually enable JIT each launch would conflict with the simple-install goal.
- [Android requires every APK to be signed before installation](https://developer.android.com/studio/publish/app-signing). Apply that signature automatically in release packaging with a retained local key; players only allow installation from the browser/file manager and install the APK. There is no developer account or store involved.

The Linux and macOS package installers should install only the authored app and dependencies. A common first-launch importer provides a real file picker and progress UI; native package scripts are unsuitable for interactive XAP selection. Windows can retain its working setup wizard, then share the same validation/preparation library and repair semantics. Document the macOS security override and AltStore setup/refresh plainly. For Android, monitor [developer verification's rollout](https://developer.android.com/developer-verification/guides/faq): an unregistered homebrew may require Android's advanced sideload flow on affected certified devices in addition to the usual unknown-sources permission.

## Shared import and runtime contract

1. Split the current desktop host into platform-neutral preparation, content, manifest, save, and game-facing services plus platform-specific window/input/display, file picker, photo picker, storage, and native library adapters. Keep the original phone DLL and proprietary files out of release artifacts. Version-pin all supported input fingerprints and tool/native dependencies for each platform.
2. On first launch with no valid base install, show an import screen. Require the supported phone XAP; offer optional supported I MAED and Time Viking art packages/directories. Validate before mutation, show source/version and needed storage, prepare into a staging area, verify hashes, and atomically activate it. Mark onboarding complete only after a successful base import. Cancel or failure keeps the importer available next launch.
3. Store prepared assets and manifests in app-controlled **persistent data**, separate from saves and the read-only program package. The game must load from this location, including after restart/update. After successful import, original XAP/Steam/360 packages can be deleted without breaking play. The app must not depend on remembered source paths. Retain the previous working asset set until replacement commits; never erase saves during reimport. Explain that uninstalling the app can remove its private imported data and saves, so backup/export may be a later feature.
4. In **Settings → Assets → Reimport**, reopen the same picker. Allow replacement of the base XAP and each existing optional source, and addition of missing optional sources. A canceled or failed import leaves the current game intact. On successful commit, save preferences, dispose the running game, and start a fresh game session so all content is reloaded. Do not ask for packages on ordinary boots once a valid install exists. The existing optional-art selection settings remain independent of the reimport action.
5. Put save paths, generated assets, logs, and manifests under each platform's app data conventions. Use a storage abstraction rather than `Directory.SetCurrentDirectory` and the current same-directory constraint. Verify generated files against the manifest at launch, offer repair through Reimport if corrupt, and preserve saves across updates and repair. Avoid broad filesystem/photo permissions when system pickers suffice.

## Display, input, and creator behavior

- Mobile has no resolution or fullscreen settings. Render landscape content to the current **usable window** with a uniform scale, fill the available width, and adjust the logical scene's width or height to the actual aspect ratio without stretching sprites. Keep a minimum scene area so original menus and gameplay fit. Place touch controls inside safe areas around cutouts, rounded corners, and system bars; test narrow, wide, tablet, and split-screen windows.
- Recompute scene size, render targets, menu positions, and the touch/mouse coordinate transform when the usable window changes. Preserve game state on rotation, Android fold/unfold or multi-window resize, and iPad window changes. If a fold hinge divides the window, keep primary UI and touch controls in safe regions. This is a required continuity test, not only an optional resolution tweak. [Android documents fold/window changes](https://developer.android.com/guide/topics/large-screens/configuration-and-continuity).
- Keep touch as the default mobile input. Support connected controller plus mouse/keyboard where the OS and device expose them; map all through the same game actions, handle hot plug/disconnect, focus, back/cancel, and pointer scaling. Hide touch overlays only when the player chooses or when a verified input mode makes that useful.
- Replace the Windows-only creator folder picker with native multi-photo selection: [iOS Photos picker](https://developer.apple.com/documentation/PhotoKit/delivering-an-enhanced-privacy-experience-in-your-photos-app) and [Android Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker). Decode JPEG, PNG, and HEIC/HEIF where the platform supplies them; apply EXIF orientation and color conversion; bound image count, size, and memory; create thumbnails and game textures on the correct graphics thread. Copy selected images or normalized thumbnails into app data so creations still work if the original photo changes or picker access expires. Preserve the current custom sprite save format or migrate it explicitly. System pickers avoid broad library permission for this workflow.

## Ordered execution and release gates

### 1. Windows: finish the current release path

- Close the existing clean-account installer, hands-on gameplay, package-audit, and rights-review gates before calling the current release done. Use the existing installer and one-time XAP import as the baseline behavior.
- Refactor shared preparation/import/storage APIs in small steps without changing the Windows player flow. Add a repair/reimport entry only after the shared transaction model is verified.
- **Gate:** clean Windows user installs offline, plays all three phone modes, optional art failure leaves the base install usable, and uninstall/reinstall preserves saves as documented.

### 2. Linux: first new desktop port

- Make launcher, hooks, bridge, content conversion, and package layout OS-neutral. Replace Win32 dialogs and paths, make native libraries and any converter available for Linux, and verify font/audio/video behavior. Produce self-contained Linux x64 `.deb`, then `.rpm`, with desktop entry/icon and first-launch importer.
- Exercise package install/update/removal, first import, launch, game modes, Settings, input, controller, creator photos, saves, and wrong/corrupt XAP behavior on native Linux.
- **Gate:** a player can install through the graphical package manager and import their XAP without SDK, terminal, or extra downloads.

### 3. macOS: second desktop port

- Port native library loading, file/photo pickers, app bundle resources, save locations, input, and the content converter. Build a self-contained `.app` and unsigned `.pkg` on a Mac; include Intel and Apple Silicon builds only after each has been tested. Keep generated content outside the app bundle.
- Test fresh install/update, Gatekeeper's manual override, XAP import, all game modes, controller/mouse/keyboard, creator photos, and save preservation on real Mac hardware. Publish a checksum and clear download instructions. [Apple documents the **Open Anyway** procedure](https://support.apple.com/en-us/102445).
- **Gate:** a Mac user can install the homebrew package, perform the one-time macOS security override, import the XAP, and play without tools or an account.

### 4. iOS: AltStore IPA and real-device runtime gate

- Prepare a reproducible macOS build workflow: pin a compatible Xcode/.NET SDK and iOS workload, build an iPhone `ios-arm64` app bundle with publisher code signing disabled, package a standard IPA, audit it for bundled proprietary material, and upload the tested IPA to GitHub Releases. .NET's iOS build exposes [`EnableCodeSigning` and `BuildIpa`](https://github.com/dotnet/macios/blob/main/docs/building-apps/build-properties.md); verify their combination with the actual host project before promising the artifact. GitHub Actions' macOS VM is enough for repeatable release builds. No Apple Developer Program account or publisher certificate should enter this workflow.
- Build a content-free IPA on a Mac and install it on a real iPhone through AltStore Classic. Validate graphics/audio/input, native file and photo pickers, writable asset storage, and app updates through the same AltStore identity. The download can be a direct IPA first; add a small AltStore Classic source JSON for discoverable updates after the install path works. Do not use AltStore PAL, which has a different publisher/notarization model.
- Prototype on-device XAP preparation and the three-song conversion without a spawned desktop executable. Test whether the prepared game assembly can load and execute with the supported iOS runtime/interpreter under normal AltStore launch, without a per-launch JIT procedure. [Microsoft's iOS runtime/AOT guidance](https://learn.microsoft.com/en-us/dotnet/maui/deployment/runtimes-compilation?view=net-maui-10.0) is the technical starting point. Do not infer device success from a simulator.
- If imported executable IL cannot run robustly, an authored, statically bundled mobile gameplay implementation that imports **data/assets only** may be necessary. That is a substantial port, but AltStore remains the intended installation method. Retain the one-time import and Reimport UI either way.
- Test installation and update with a regular Apple ID, AltServer refresh at the seven-day boundary, preservation of imported assets and saves, and all three game modes on a real device. Provide short AltStore setup instructions covering Windows/Mac AltServer, Apple ID, trust/Developer Mode, and refresh.
- **Gate:** a player installs the prebuilt IPA through AltStore Classic, imports their XAP once, plays and reimports on a real device, and refreshes the app without building it or joining the paid Developer Program.

### 5. Android: mobile host and APK

- Reuse mobile importer, display/input, photos, saves, and asset storage decisions. Since FNA does not support Android, prototype a supported Android host (MonoGame is a candidate) and measure the XNA ABI/content gaps plus `ZombiesWP7.dll` loading/preparation on a real device. If importing executable code is not robust, use an authored gameplay implementation instead of promising a simple FNA build.
- Generate and retain a private release key, sign the APK automatically during packaging, and distribute that prebuilt APK directly. This needs no developer account and imposes no signing work on players; keeping the same key allows app updates. Test browser/file-manager unknown-sources permission, direct install/update, all modes, controllers/keyboard/mouse, photo import, background/resume, fold/unfold, storage pressure, and repair. Test the extra advanced sideload flow on affected certified Android devices as verification expands. [Android requires signed APKs](https://developer.android.com/studio/publish/app-signing).
- **Gate:** a user downloads and installs the APK through device settings, selects packages once, deletes the original packages if desired, and plays/reimports without a computer or developer account.

## Decisions to revisit at the mobile gate

- Whether the prepared phone DLL can execute on iOS under a normal AltStore launch, using a supported interpreter configuration without a manual JIT step. This is the main iOS feasibility gate after choosing AltStore for installation.
- Whether an optional AltStore Classic source improves updates enough to justify its maintenance; a direct IPA is the initial artifact.
- Whether a distributable authored mobile game implementation is possible within the project's preservation and licensing constraints. This decides the technical iOS path if distribution is later possible and whether Android can share one code path.
- Exact supported mobile OS versions, device GPU targets, and storage budget after real-device prototypes; do not pin them from desktop assumptions.
